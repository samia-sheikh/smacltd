 What is SMAC?

  SMAC is a multi-purpose web platform that combines:
  1. Social Networking (like a mini Facebook — posts, stories, likes, comments,
  follow)
  2. Online Courses (like Udemy — buy and learn courses)
  3. Product Marketplace (like an e-commerce store)
  4. Services Marketplace (hire/buy services)
  5. Real-time Chat (messaging between users)
  6. Admin Dashboard (for managing everything)

  ---
  Data Flow — Step by Step

  Here's how data moves through the app:

  1. App Starts (index.js)

  User opens the app
    → index.js loads
      → Sets up Redux Store (global state)
      → Sets up Redux Persist (saves state to localStorage so it survives page
  refresh)
      → Wraps app in Google OAuth Provider
      → Wraps app in MUI Theme Provider (teal/white theme)
      → Renders <App />

→ index.js 
→ Redux Store 
→ Redux Persist 
→ Google Login 
→ MUI Theme ل
→  App 

  2. Routing (config/routers.js)

  <App /> renders the Router
    → Router checks the URL
      → Public routes: /signin, /signup, /about-us, /blogs, etc.
      → Protected routes: /feed, /profile, /messaging, /courses, etc.
        → ProtectedRoute checks: Does the user have a token?
          → YES → Show the page
          → NO  → Redirect to /signi

  3. Authentication Flow

  User fills in email + password on /signin
    → Formik handles form state
    → Yup validates (email format, password 8-16 chars)
    → useFetch hook sends POST /api/auth/user/login to backend
    → Backend returns { user, token }
    → Redux dispatch: setUserAuth({ user, token })
    → Token stored in Redux (persisted to localStorage)
    → Socket.io connects with the token (for real-time features)
    → User redirected to /feed

  Google Sign-in works similarly but sends the Google access token to
  /api/auth/user/login/google.



  4. Fetching Data (the useFetch hook)

  This is the central data-fetching mechanism:

  Any page/component needs data
    → Calls useFetch() hook
      → fetchData(url, reduxAction)
        → Axios GET request to backend (https://smacltd.com/api/...)
        → Attaches Authorization: Bearer <token> header
        → On success: dispatches Redux action to store data
        → On 401 error: auto-logs out the user
        → On other errors: shows toast notification


  5. State Management (Redux)

  The app has 21 Redux slices — think of each as a "drawer" holding specific
  data:

  Redux Store
  ├── user          → { token, user } (who's logged in)
  ├── post          → { posts, otherUserPosts }
  ├── follow        → { followers, following }
  ├── conversations → { conversations, selectedConversation }
  ├── socket        → { socket connection, selectedChat }
  ├── notificatations → { all notifications }
  ├── globalSearch  → { searchValue, users, posts, products, courses, services }
  ├── parentCategories → { course/product/service categories }
  ├── subscription  → { pricing data }
  ├── addProduct    → { productDetails, productImages } (for creating)
  ├── addService    → { serviceDetails, serviceImages }
  ├── refundTicket  → { ticket data }
  ├── paymentResponse → { payment status }
  └── ... (more slices)

  Redux Persist saves this entire store to localStorage, so when you refresh the
   page, you don't lose your login or data.



  
"In our application, we use Redux for centralized state management. Think of the Redux store as a single source of truth that holds all global data.

The store is divided into multiple slices — around 21 — and each slice manages a specific domain of the application. For example, the user slice stores authentication data like token and user info, the post slice manages posts, the conversations slice handles messaging data, and the globalSearch slice manages search results.

Whenever the app fetches data from the backend using our custom useFetch hook, the response is dispatched to the relevant Redux slice. This ensures predictable state updates and automatic UI re-rendering.

We also use Redux Persist, which saves the entire Redux store into localStorage. So even if the user refreshes the page, the authentication token and other important data remain intact.

This architecture keeps the app scalable, organized, and easy to maintain."


6. Real-Time Features (Socket.io)

  User logs in
    → Socket connects to ws://34.205.160.246:5000 with auth token
    → Socket middleware in Redux handles events:

    SENDING:
      sendMessage      → Sends a chat message
      sendRefundMessage → Sends a refund support message
      notificationRead → Marks notification as read

    RECEIVING:
      notifyMessage      → New chat message arrives → update Redux
      newNotification    → New notification → update Redux
      newRefundMessage   → Refund chat update → update Redux
      unReadNotifications → All unread notifications on connect


  7. Page Rendering Flow (Example: Feed Page)

  User navigates to /feed
    → ProtectedRoute verifies token ✓
    → HomePage.jsx renders
      → Layout component wraps the page (Header + Footer + Helmet for SEO)
      → Header shows navigation, notifications bell, profile picture
      → Posts component loads
        → useFetch calls GET /api/user/post
        → Posts arrive → dispatched to Redux (post slice)
        → Component re-renders with posts
        → Infinite scroll loads more posts as user scrolls down
      → Each post shows: content, images, like/comment/share buttons
        → Like → API call → update Redux
        → Comment → opens comment modal → API call → update Redux
        → Share → opens share modal


  8. Creating Content (Products, Courses, Services)

  User clicks "Add Product" (example)
    → Multi-step form opens (modal)
    → Step 1: Product details (title, description, price, category)
      → Saved to Redux addProduct slice
    → Step 2: Upload images
      → Saved to Redux addProduct slice
    → Step 3: Review & Submit
      → useFetch.postData(POST /api/product, formData)
      → Backend saves product
      → Success toast notification
      → Product appears in marketplace

  9. Payment Flow

  User wants to buy a course/product
    → Navigates to /pricing
    → Selects a subscription plan
    → Payment form appears
    → Submits payment details
      → POST /api/payment
      → Backend processes payment
      → Redirects to /payments/response
      → SuccessfulPaymentResponsePage shows result

  10. Admin Dashboard Flow

  Admin logs in (role: "admin")
    → usePermission hook checks "admin.dashboard" permission ✓
    → /admin/dashboard loads
      → Sidebar with: Users, Courses, Products, Services, Payments, Refunds,
  Categories
      → Each section shows CRUD (Create, Read, Update, Delete) tables
      → Example: Manage Courses
        → Fetches all courses from API
        → Displays in table
        → Can add/edit/delete courses
        → Can manage course categories

  ┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
  │   Browser    │────▶│  React App   │────▶│   Redux Store   │
  │  (User)      │     │  (Components)│◀────│  (21 slices)    │
  └─────────────┘     └──────┬───────┘     └────────┬────────┘
                             │                       │
                      ┌──────▼───────┐        ┌──────▼────────┐
                      │  useFetch    │        │ Redux Persist  │
                      │  (Axios)     │        │ (localStorage) │
                      └──────┬───────┘        └───────────────┘
                             │
                      ┌──────▼───────┐     ┌─────────────────┐
                      │  Backend API │     │   Socket.io     │
                      │ smacltd.com  │     │  (Real-time)    │
                      └──────────────┘     └─────────────────┘

  1. User interacts with the browser
  2. React components render the UI and handle user actions
  3. useFetch hook (Axios) talks to the backend API for data
  4. Redux Store holds all app state (21 slices for different features)
  5. Redux Persist saves state to localStorage (survives refresh)
  6. Socket.io handles real-time chat and notifications
  7. Protected Routes ensure only logged-in users access private pages

  The app is essentially a full-featured social + marketplace platform with
  real-time messaging, course management, and an admin panel — all built as a
  React single-page application.

  ---
  Tab 1: Users Management

  File: DashboardUser.jsx

  What the admin can do:
  - View all registered users in a table
  - Filter by: All / Active / Blocked
  - Search users by name or email (with 300ms debounce)
  - Block/Unblock users via a dropdown menu on each row
  - Click a user to see their full details in a side panel

  Data Flow:
  Page loads
    → GET /api/admin/user → displays all users in table

  Admin clicks filter "Blocked"
    → GET /api/admin/user?isBlocked=true → filtered results

  Admin searches "john"
    → GET /api/admin/user?filter=john → search results

  Admin clicks "Block" on a user
    → PUT /api/admin/user (with user data) → user blocked
    → Table refreshes

  Admin clicks a user row
    → Redux: setDashboardUser(user) → side panel shows full details

  Table columns: Profile Picture | Name | Email | Status | Actions
  (Block/Unblock)

  Tab 2: Courses Management

  File: DashboardCourses.jsx

  What the admin can do:
  - View all courses on the platform
  - Search for courses or filter by instructor
  - View course details in a modal (title, description, duration, class days,
  instructor info)
  - Delete courses via dropdown menu
  - Navigate to full course page via "More..." button

  Data Flow:
  Page loads
    → GET /api/admin/course → all courses displayed

  Admin searches by instructor email
    → DashBoardSearchInputField shows suggested users as chips
    → Click a user chip → GET /api/admin/course/{email} → that user's courses

  Admin clicks a course row
    → DashBoardModal opens showing:
      - Title, Description, Created date
      - Course mode, duration, class days
      - Instructor name + link to profile

  Admin clicks delete
    → DELETE /api/admin/course/{courseId} → course removed → table refreshes

  Table columns: Image | Title | Instructor | Listed Date | Status | Actions
  (Delete)

  ---
  Tab 6: Refund Tickets

  File: RefundTickets.jsx

  What the admin can do:
  - View all refund requests from users
  - Search tickets
  - Open individual tickets for detailed review
  - Approve or reject refund requests (with reason for rejection)
  - Chat with the user about the refund

  Data Flow:
  Page loads
    → GET /api/refundTickets/admin → all tickets in table

  Admin clicks "Open" on a ticket
    → Navigates to /refund/ticket/{refundId} (courses)
    → OR /refund/service/ticket/{refundId} (services)

  On the detail page:
    → GET /api/course/orders/refunds/{ticketId} → ticket details
    → GET /api/refundchat/{ticketNumber} → chat messages

  Admin changes status dropdown:
    → "Approved" → PUT /api/admin/course/orders/refunds/{refundId}
        payload: { status: "Approved", orderId }
    → "Rejected" → reason input appears
        payload: { status: "Rejected", orderId, reasonForRejected: "..." }

  Table columns: Ticket # | Service Provider | Complaint (user) | Service Name |
   Status (color badge) | Actions (Open)

  Status colors:
  - Pending → Yellow
  - Approved → Green
  - Rejected → Red

  Complete Data Flow Summary

  As a Creator/Seller:

  Create content
    → "Add Course/Service/Product" button → Modal form → POST to API
    → Item appears in "My Courses/Services/Market" list

  Manage content
    → View details (click row → detail page)
    → Delete content (dropdown → DELETE API)
    → View who purchased (applicants table on detail page)

  Earn money
    → Buyers purchase your items → money accumulates
    → Payment tab shows: Total Earned, Available Balance
    → Request withdrawal → modal → POST → admin approves

  Handle refunds (as seller)
    → "My Refund Requests" tab shows tickets against your items
    → View ticket → chat with buyer/admin about resolution

  As a Buyer:

  View purchases
    → "Purchased Courses/Services" sub-tabs
    → Click row to see details

  Request refund
    → Dropdown → "Request Refund" → enter reason → POST
    → Ticket created → appears in "Requested Refund Tickets" tab
    → View ticket detail → chat with seller/admin
    → Wait for admin to Approve/Reject

  Track payments
    → Subscriptions tab shows payment history
    → Status color-coded (green/yellow/red)

      → Duplicate posts filtered by postId
      → Page number increments
      → Loading spinner shows during fetch

  Follow/Unfollow System

  Follow States

  Three possible states for any user relationship:

  1. NOT FOLLOWING (false)
     → Button shows: "Follow"
     → Action: POST /api/user/connection { followingEmail }
     → Changes to: PENDING

  2. PENDING (request sent, awaiting acceptance)
     → Button shows: "Pending"
     → Action: DELETE /api/user/connection/following/{email}
     → Changes to: NOT FOLLOWING (cancels request)

  3. ACCEPTED (following)
     → Button shows: "Following" or "Unfollow"
     → Action: DELETE /api/user/connection/following/{email}
     → Changes to: NOT FOLLOWING

CHAT MESSAGING FEATURES
 Architecture Overview

  The messaging system has two separate chat systems:

  1. Regular Chat — direct messaging between users (like DMs)
  2. Refund Chat — support chat within refund tickets (between buyer, seller,
  and admin)

  Both use Socket.IO for real-time messaging + REST APIs for loading history.

  ┌────────────────────────────────────────────────┐
  │                MESSAGING SYSTEM                │
  │                                                │
  │  ┌──────────────┐      ┌───────────────────┐   │

  │  │ (1-on-1 DMs) │      │ (support tickets) │   │
  │  └──────┬───────┘      └────────┬──────────┘   │
  │         │                       │               │
  │         └───────┬───────────────┘               │
  │                 ▼                                │
  │         ┌──────────────┐                        │
  │         │  Socket.IO   │ (real-time transport)  │
  │         │  + REST APIs │ (message history)      │
  │         └──────────────┘                        │
  │                 ▼                                │
  │         ┌──────────────┐                        │
  │         │ Redux Store  │ (state management)     │

  ---
  Socket.IO Connection

  File: src/Socket/socket.js

  Server:  ws://34.205.160.246:5000
  Auth:    JWT token from localStorage
  Transport: WebSocket only
  Reconnection: Enabled (auto-reconnect)

  When does the socket connect?

  User logs in successfully
    → Token saved to Redux (persisted to localStorage)
    → Header component mounts
    → Dispatches { type: "connect" }
    → Socket middleware intercepts
    → Creates socket connection with token
    → Registers all event listeners
    → Dispatches socketConnected()

  When does it disconnect?

  User logs out
    → Dispatches { type: "user/logout" }
    → Socket middleware intercepts
    → Calls socket.disconnect()
    → Socket destroyed

  ---
  Socket Events

  Events the app SENDS to the server:
  Event: sendMessage
  Data: { content, chatId } or { content, receiverEmail }
  Where Used: ChatBox, Chat dialog, ChatFromOtherUser
  ────────────────────────────────────────
  Event: sendRefundMessage
  Data: { msgContent, room: chatId, msgType: "text"/"image_url" }
  Where Used: RefundChatSection
  ────────────────────────────────────────
  Event: notificationRead
  Data: { notificationId }
  Where Used: AllNotifications
  ────────────────────────────────────────
  Event: clearNotifications
  Data: { notificationIds: [] }
  Where Used: Notifications
  Events the app LISTENS for from the server:
  Event: connect
  What Happens: Socket connected
  Redux Action: socketConnected()
  ────────────────────────────────────────
  Event: notifyMessage
  What Happens: New chat message arrives
  Redux Action: receiveMessage(message)
  ────────────────────────────────────────
  Event: newRefundMessage
  What Happens: New refund chat message
  Redux Action: receiveRefundChatMessage(message)
  ────────────────────────────────────────
  Event: unReadNotifications
  What Happens: All unread notifications on connect
  Redux Action: getAllNotifications(data)
  ────────────────────────────────────────
  Event: newNotification
  What Happens: Real-time new notification
  Redux Action: newNotification(data)
  ────────────────────────────────────────
  Event: disconnect
  What Happens: Socket lost connection
  Redux Action: —

  Sending a Message (End-to-End Flow)

  1. User types "Hello!" in ChatBox input
     │
  2. User clicks Send (or submits form)
     │
  3. handleMessageSubmit() fires
     │
  4. Creates messageData:
     │  { content: "Hello!", chatId: "abc123" }
     │
  5. Socket.emit("sendMessage", messageData)
     │
     ▼ ─── Goes to server via WebSocket ───
     │
  6. Server processes message, saves to DB
     │
  7. Server emits "notifyMessage" to the receiver
     │
     ▼ ─── Receiver's browser ───
     │
  8. Socket middleware catches "notifyMessage"
     │
  9. Dispatches receiveMessage(message) → Redux
     │
  10. socketReducer: state.socket.messages = [message]
      │
  11. ChatBox.js useEffect watches state.socket.messages
      │
      ├── If message.chatId === current chat:
      │     → Append to selectedConversation
      │     → Message appears in chat
      │     → Auto-scroll to bottom
      │     → Conversation moves to top of sidebar
      │
      └── If message.chatId !== current chat:
            → Update sidebar only
            → Show 🔴 unread indicator (isSent: false)
            → Don't open that chat

  Refund Chat Features

  Text Messages:
  User types message → clicks Send
    → Socket.emit("sendRefundMessage", {
        msgContent: "I'd like a refund...",
        room: chatId (ticket number),
        msgType: "text"
      })
    → Message appears in chat

  Image Messages:
  User clicks 📷 icon → selects image
    → Image preview shown below input
    → User clicks Send
    → POST /api/refundchat/upload (FormData with image)
    → Server returns image URL(s)
    → Socket.emit("sendRefundMessage", {
        msgContent: JSON.stringify(["https://image-url.jpg"]),
        room: chatId,
        msgType: "image_url"
      })
    → Image displayed in chat as clickable thumbnail

  Image Preview:
  User clicks an image in chat
    → Redux: setImageToPreview(imageUrl)
    → ViewImageModel opens (full-screen preview)
    → Click X or outside → closes

  Disabled State:
  If refundTicket.status !== "Pending":
    → Input field disabled
    → Send button disabled
    → No more messages can be sent
    → Chat becomes read-only

  Receiving Refund Messages (Real-Time)

  Socket middleware listens for "newRefundMessage"
    → Dispatches receiveRefundChatMessage(message)
    → socketReducer: state.socket.refundChatMessage = message
    → RefundChatSection watches this state
    → If message.room === current ticket chatId:
      → Append to refundMessages
      → Auto-scroll to bottom

  Route Protection System

  File: src/config/routers.js

  ProtectedRoute (for authenticated pages)

  function ProtectedRoute({ children, permission }) {
    // 1. Check if user has a token
    if (!token) → Redirect to /signin (saves current URL in state)

    // 2. Check if user has required permission (e.g., admin.dashboard)
    if (token && permission && !hasPermission(permission)) → Redirect to /feed

    // 3. All good → Render the page
    return children
  }

  ProtectedAuthRoute (for auth pages — redirect if already logged in)

  function ProtectedAuthRoute({ children }) {
    // If user is already logged in
    if (token) → Redirect to /feed (or to the URL they came from)

    // Not logged in → Show the auth page
    return children
  }

  Permission System (usePermission hook)

  Roles:
    admin: "admin"
    user:  "user"

  Permissions:
    "user.dashboard"  → [user]
    "admin.dashboard" → [admin]

  hasPermission("admin.dashboard")
    → checks if user.role is in ["admin"]
    → returns true/false

  Token Management

  Where the token lives:

  1. Redux state: state.user.token
       → Used by useFetch hook to build Authorization headers
       → Accessible via useSelector((state) => state.user)

  2. localStorage (via Redux Persist): persist:root
       → Survives page refresh / browser close
       → Key path: persist:root → user → token
       → Socket uses this as fallback

  3. Authorization Header: Bearer {token}
       → Attached to every API request via getHeaders()
       → Both JSON and FormData requests include it

  Token lifecycle:

  Login/Signup → token received from API
    → Stored in Redux → persisted to localStorage
    → Included in every API call header
    → Passed to Socket.io for auth

  API returns 401 → useFetch catches it
    → Dispatches logout()
    → Redux: token = null, user = null
    → localStorage updated
    → ProtectedRoute redirects to /signin

  User clicks Logout
    → Same logout() flow
    → Socket disconnects

  Search Flow

  User types "react" in search bar → presses Enter
    │
    ├── handleGlobalSearch(event) fires
    │
    ├── GET /api/search?searchQuery=react
    │
    ├── Server returns:
    │   {
    │     users: [...],      ← matching users
    │     posts: [...],      ← matching posts
    │     products: [...],   ← matching products
    │     courses: [...],    ← matching courses
    │     services: [...]    ← matching services
    │   }
    │
    ├── Redux dispatches (all at once):
    │   dispatch(setSearchValue("react"))
    │   dispatch(setUsers(res.users))
    │   dispatch(setPosts(res.posts))
    │   dispatch(setProducts(res.products))
    │   dispatch(setCourses(res.courses))
    │   dispatch(setServices(res.services))
    │
    └── Navigate to /search?searchQuery=react

  Key detail: There is no debounce on the global search. It only fires on Enter
  key press. The useDebounce hook exists in the codebase but is not used here.

  Redux State for Search

  Redux Store
  │
  └── globalSearch (globalSearchSlice)
      ├── searchValue: "react"           ← the search query
      ├── users: [{...}, {...}]          ← user results
      ├── posts: [{...}, {...}]          ← post results
      ├── products: [{...}, {...}]       ← product results
      ├── courses: [{...}, {...}]        ← course results
      └── services: [{...}, {...}]       ← service results

  All set at once from a single API call, then read independently by each tab.

  Part 2: Custom Hooks

  1. useFetch — Primary Data Fetching

  File: src/features/hooks/useFetch.js

  The most important hook in the entire app. Every API call goes through this.

  State

  const [res, setResponse] = useState(null)     // API response
  const [loading, setLoading] = useState(false)  // loading flag
  const [error, setError] = useState("")         // error message
  const [success, setSuccess] = useState(false)  // success flag

  Methods

  fetchData(url, cbFunction, setLocalState) — GET

  fetchData("/api/user/post", setMultiplePost, setLocalPosts)
    │
    ├── Sets loading = true
    ├── Builds headers: { Authorization: "Bearer {token}", Content-Type:
  "application/json" }
    ├── GET https://smacltd.com{url}
    │
    ├── On success:
    │     ├── Sets res = response.data
    │     ├── If cbFunction → dispatch(cbFunction(response.data))  ← Redux
  dispatch
    │     └── If setLocalState → setLocalState(response.data)      ← local state
    │
    ├── On 401 error:
    │     └── dispatch(logout())  → clears token, redirects to /signin
    │
    └── On other errors:
          └── Toast notification with error message

  postData(url, payload, cbFunction, resetToken, formData, setLocalState,
  notification) — POST

  postData("/api/user/post", formData, setPost, null, true, null, true)
    │
    ├── Token: uses resetToken if provided, else Redux token
    ├── Headers: multipart/form-data if formData=true, else application/json
    ├── POST https://smacltd.com{url} with payload
    │
    ├── On success:
    │     ├── dispatch(cbFunction(response)) if provided
    │     ├── setLocalState(response) if provided
    │     ├── Toast "Success!" if notification=true (default)
    │     └── Sets success = true
    │
    └── On 401: dispatch(logout())

  patchData(url, payload, cbFunction, setValues, formData) — PATCH

  Same pattern. Special: catches "Invalid old password" without logging out (for
   password change).

  patchPass(url, payload, cbFunction, setValues, formData, tokenParam) — PATCH
  with custom token

  Used for password reset where the token comes from URL, not Redux.

  putData(url, payload, cbFunction, setValues, formData) — PUT

  Same pattern as patchData.

  deleteData(url, setLocalState) — DELETE

  deleteData("/api/user/post/abc123", (res) => filterOutDeletedPost(res))

  fetchMultipleData(urls[], cbFunctions[], payloads[]) — Concurrent POSTs

  Uses axios.all() for parallel requests. Dispatches multiple Redux callbacks
  sequentially.

  Return

  return {
    res, loading, error, success,
    fetchData, postData, patchData, patchPass, putData, deleteData,
  fetchMultipleData
  }

  8. useInfiniteScroll — Pagination Hook

  File: src/features/hooks/infiniteScroll.js

  const { isFetching, setIsFetching, fetchScrollData } = useInfiniteScroll()

  useEffect(() => {
    if (!isFetching) return
    fetchScrollData(setPosts)
  }, [isFetching])

  How it works:

  User scrolls page
    → Debounced scroll handler (500ms)
    → Check: scrolledDistance >= totalPageHeight - 1000px (footer offset)
    → If near bottom AND not already fetching:
        → isFetching = true
        → GET /api/user/post?limit=6&page={nextPage}
        → Merge new posts with existing
        → Remove duplicates (by postId)
        → page++
        → isFetching = false

  Configuration:
  - Page size: 6 posts per request
  - Debounce: 500ms
  - Footer offset: 1000px
  - Deduplication: by postId

  9. useSocket — Socket Event Emitter

## 2.5 Authentication - Deep Dive

**Sign-In Flow (Email):**
1. Formik form with Yup validation (email format, password 8-16 chars)
2. POST /api/auth/user/login { email, password }
3. Server returns { user, token }
4. Redux dispatch: setUserAuth({ user, token })
5. Token persisted to localStorage via Redux Persist
6. Socket.IO connects with token
7. Navigate to /feed

**Sign-In Flow (Google):**
1. useGoogleLogin() opens Google consent screen
2. Google returns access_token
3. POST /api/auth/user/login/google { accessToken }
4. Backend exchanges Google token, creates/finds user, returns JWT
5. Same Redux + Socket + Navigate flow as email

**Sign-Up Flow:**
1. Stricter validation (3-16 char names, letters only, password: uppercase + number + special char)
2. POST /api/auth/user/register-user
3. Server creates account + sends verification email
4. Verification modal shown -> user clicks link in email
5. GET /api/auth/user/verify-email?jwt={token}
6. Account activated -> user can sign in

**Password Reset:**
1. User enters email on /password page
2. PATCH /api/user/forgot-password { email }
3. Server sends reset link: /new-password?jwt={resetToken}
4. User sets new password (with confirmation)
5. PATCH /api/user/setnew-password with reset token in Authorization header

For scaling, the backend API at smacltd.com can be horizontally scaled behind a load balancer, and the Socket.IO server supports clustering.
